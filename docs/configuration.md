# Конфигурация приложения

[← README](../README.md) · [Данные](data-contracts.md) · [WS](websocket.md)

Все настройки текущей версии находятся в [app.js](../app.js), исходном `date_config`, панели потока или query-параметрах URL. Отдельного конфигурационного JSON, `.env` и backend-настроек нет. Имена функций ниже удобны для поиска по файлу; они находятся внутри замыкания и не доступны через `window`.

## Основные значения

| Настройка | По умолчанию | Где менять | Действие |
| --- | --- | --- | --- |
| `CONFIG.slotStepMinutes` | `15`, минуты | Объект `CONFIG` | Шаг начала назначения через форму и drag-and-drop |
| `CONFIG.minGapMinutes` | `30`, минуты | `CONFIG` | Минимальный промежуток между назначениями одного специалиста |
| `CONFIG.workingWeekdays` | `[1, 2, 3, 4, 5]` | `CONFIG` | Разрешённые дни назначения: JS-нумерация, 0 — воскресенье, 6 — суббота |
| `CONFIG.mockHttpDelayMs` | `260`, мс | `CONFIG` | Задержка mock-загрузки и значение по умолчанию для создания/загрузки завтрашнего дня |
| `CONFIG.mockWsIntervalMs` | `10000`, мс | `CONFIG`, далее панель потока | Начальный интервал эмулятора WS |
| `CONFIG.mockWsMaxMessages` | `100`, сообщений | `CONFIG`, далее панель потока | Начальный предел генерации |
| `date_config.time_begin` | `08:00` | `mockResponse()` или входящий полный контекст | Начало рабочего дня |
| `date_config.time_end` | `17:00` | Там же | Конец рабочего дня |
| `date_config.break_begin` | `12:00` | Там же | Начало обеда |
| `date_config.break_end` | `12:45` | Там же | Конец обеда |
| Обновление временных подсказок | `30000`, мс | Последний `setInterval()` в `app.js` | Обновляет подсказки и доступность действий; статусы автоматически не меняет |

`CONFIG` заморожен через `Object.freeze`: его меняют в исходнике с последующей перезагрузкой, а не присваиванием из консоли. Форма настройки рабочего дня, обеда, шага и промежутка пока не реализована. UI-настройки есть только у потока.

При изменении шага или промежутка обновите и связанные места в [index.html](../index.html), поскольку они пока статические:

| Изменение | Сопутствующее место в HTML |
| --- | --- |
| `slotStepMinutes` | У поля `#assignment-time` атрибут `step` задан в секундах: `900` для 15 минут. Установите `slotStepMinutes × 60` |
| `minGapMinutes` | Обновите текст `.gap-note`, `#completion-hint` и `#create-duration-hint`: сейчас в них указано «30 минут» / «30 мин» |

JS-валидатор, drag-and-drop и динамические правила формы читают `CONFIG`, но перечисленные HTML-значения автоматически с ним не синхронизируются.

Шаг 15 минут относится к **началу**, а не к обязательной кратности длительности. Длительность — положительное целое число минут. Например, событие 10:00–10:37 допустимо при выполнении остальных правил; после него требуется промежуток до 11:07, а ближайшее допустимое начало на сетке 15 минут — 11:15.

Промежуток проверяется с обеих сторон события. Ровно 30 минут допустимо. Обед запрещает пересечение, но отдельный 30-минутный отступ от границ обеда не добавляется: задача может закончиться в 12:00 или начаться в 12:45. Аналогично нет дополнительного отступа от начала/конца рабочего дня.

Если меняете рабочие дни, согласуйте с ними также `isWeekend` в `mockResponse()`: сейчас генератор отдельно считает субботу и воскресенье выходными и не создаёт для них исходных назначений. Сам запрет назначения опирается на `CONFIG.workingWeekdays`. Навигация показывает все семь дней недели независимо от этой настройки.

## Рабочее время и обед

В `mockResponse()` поля задаются через `timeValue(число_минут_от_полуночи)`. Например, 480 — 08:00, 720 — 12:00. В JSON тот же блок выглядит так:

```json
{
  "date": "2026-11-02T00:00:00",
  "time_begin": "0001-01-01T08:00:00",
  "time_end": "0001-01-01T17:00:00",
  "break_begin": "0001-01-01T12:00:00",
  "break_end": "0001-01-01T12:45:00"
}
```

Это значение `date_config`, а не полный ответ для `UpdateData`. Пример полного ответа приведён в [контрактах](data-contracts.md).

Порядок должен быть строго таким:

```text
начало дня < начало обеда < конец обеда < конец дня
```

Текущая модель предусматривает один обязательный обед внутри одного дня. Отключение обеда через `null`, несколько перерывов, индивидуальные обеды специалистов и ночные смены не поддерживаются. Расписание и обед общие для специалистов выбранного контекста «подразделение + дата».

После изменения рабочего времени скорректируйте исходные назначения в `mockResponse()`: задача за пределами дня или с несогласованной длительностью не пройдёт нормализацию. Изменение конфигурации не пересоставляет уже существующие назначения автоматически.

## Таймеры и управление потоком

В панели потока укажите интервал в **секундах** и предел, затем примените настройки:

- Интервал: целое число от 1 до 300 секунд. В состоянии хранится в миллисекундах.
- Предел: целое число от 1 до 1000 обращений.
- «Пауза» останавливает автоматическую генерацию; «Возобновить» запускает её снова.
- Счётчик общий для демо, не отдельный для каждой даты/подразделения. Повышение предела разрешает продолжение; если включена ручная пауза, её нужно снять.
- Уменьшение предела не удаляет полученные задачи и не обнуляет счётчик.

Используется один повторно устанавливаемый `setTimeout`: следующий интервал отсчитывается после обработки предыдущего сообщения. Это имитация поступлений, а не гарантия точной периодичности. Фоновая вкладка может замедлять браузерные таймеры. Пока расписание загружается, очередной цикл не генерирует задачу.

`mockHttpDelayMs` — искусственная задержка ответа, **не сетевой таймаут**. У загрузки завтрашнего контекста есть собственная задержка, после которой при отсутствии кэша выполняется обычный `mockHttp.load()`. По умолчанию это примерно 260 + 260 мс; для кэшированного завтрашнего контекста — примерно 260 мс. Отдельной политики timeout/retry настоящего HTTP-клиента нет.

## Что имеет приоритет над исходными значениями

Сохранённые настройки потока восстанавливаются поверх начальных значений `CONFIG`. Кэшированные и восстановленные контексты содержат собственный `date_config` и задачи. Поэтому изменение генератора в коде не обязательно изменит уже сохранённую дату.

Чтобы проверить новые исходные настройки:

1. Сохраните изменения в `app.js`.
2. Перезагрузите страницу с обновлением файлов из сервера.
3. Откройте `?mockStorage=memory` для нового изолированного набора данных. Либо подтвердите «Сбросить демо», если сохранённые данные больше не нужны.

Обычный reload сохраняет демо и не равен сбросу. Настройки шага и промежутка читаются из текущего кода, но существующие задачи не перемещаются автоматически под новые правила.

## Демо-параметры URL

Параметры считываются при загрузке страницы. Пример объединения:

```text
http://127.0.0.1:8765/?mockStorage=memory&mockNow=2026-11-02T09:37&mockCreateDelay=1800
```

| Параметр | Значение | Поведение |
| --- | --- | --- |
| `mockNow` | `YYYY-MM-DDTHH:mm` | Фиксирует локальные демо-часы, включая дату по умолчанию; время не идёт. Некорректное значение игнорируется |
| `mockStorage` | `memory` | Отдельное хранилище в памяти, исчезает при reload; открывает диагностическую форму WS |
| `mockStorage` | `corrupt` | Изолированное повреждённое сохранение для проверки восстановления |
| `mockStorage` | `unavailable` | Изолированные ошибки чтения, записи и удаления |
| `mockStorage` | `write-error` | Изолированная ошибка записи |
| `mockError` | `once` | Ошибка первого вызова `mockHttp.load()`; последующий вызов может пройти |
| `mockCreateError` | `once` | Ошибка первого mock-запроса создания ручного события |
| `mockCreateDelay` | Число `260…5000`, мс | Задержка создания; вне диапазона используется `CONFIG.mockHttpDelayMs` |
| `mockTomorrowError` | `once` | Ошибка первой загрузки через `loadTomorrow()` |
| `mockTomorrowDelay` | Число `260…5000`, мс | Начальная задержка `loadTomorrow()`; при промахе кэша добавится задержка `load()` |
| `mockTargetDate` | `YYYY-MM-DD` | Дата для применения сценария `mockTargetCase`; требуется изолированный `mockStorage` |
| `mockTargetCase` | `lunch` | Для целевой даты обед 09:30–10:15 |
| `mockTargetCase` | `readonly` | Для целевой даты запрет изменения подразделения |
| `mockTargetCase` | `absence` | Отсутствие специалиста с ID `<departmentId>-engineer-10`, если он есть; в стандартных данных это medical |
| `mockTargetCase` | `gap` | Задача 10:15–11:15 у того же специалиста для проверки промежутка |
| `mockData` | `long-text` | Длинные имя, модель и описание; только при `mockStorage=memory` |
| `mockData` | `invalid-text` | Некорректный тип описания в первом ответе генератора; только при `mockStorage=memory` |
| `mockWsOnDrag` | `once` | Одно входящее сообщение при первом активном pointermove перетаскивания; только при `mockStorage=memory` |

Режимы ошибок storage не обращаются к обычному `localStorage`. Используйте перечисленные значения: неизвестное непустое значение `mockStorage` технически тоже включает память, но не включает форму WS и сценарии, требующие именно `memory`. При `mockError=once` восстановленный кэш может исключить сам вызов загрузки — для воспроизведения используйте отдельное демо в памяти. Ошибку первого `load()` также может получить обработчик потока, если именно он первым запросит незагруженный контекст.

Пример проверки конфликта переноса на завтра:

```text
http://127.0.0.1:8765/?mockStorage=memory&mockNow=2026-11-02T09:37&mockTargetDate=2026-11-03&mockTargetCase=lunch
```

Параметры не назначают задачи сами. Подготовьте назначение, пересекающее целевой обед, и выполните перенос в карточке.

## Хранилище и время

Ключ — `gmt-board.demo.v1`, версия снимка — `1`. Сохраняются `selection`, массив `contexts` с `raw` и `taskStates`, а также `stream` с настройками, счётчиком и принятыми ID сообщений. Снимки прежней версии 1 без `stream` поддерживаются. Это внутренний формат демо, не контракт серверного API.

При ошибке чтения или записи интерфейс показывает причину и продолжает работать в памяти. До сброса попытки сохранения блокируются. Сброс затрагивает только ключ этого приложения. Если удаление недоступно, старое сохранение может вернуться после перезагрузки — интерфейс сообщает об этом.

Календарь и `mockNow` используют локальный часовой пояс браузера. Отдельной настройки серверного часового пояса нет. Время расписания передаётся без `Z` и смещения; фактические времена и история хранятся через `toISOString()` и показываются в локальном времени. Выбор даты ограничен годами 2000–2099.
