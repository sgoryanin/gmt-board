# WS: эмулятор и контракт входящих сообщений

[← README](../README.md) · [Конфигурация](configuration.md) · [Модели](data-contracts.md) · [Архитектура](architecture-and-mocks.md)

## Что реализовано

В [app.js](../app.js) есть генератор JSON-сообщений и единый обработчик их приёма. **Настоящее WebSocket-соединение не открывается**: нет WS URL, handshake, серверного процесса, авторизации, reconnect, heartbeat или сетевых подтверждений. Запуск Python-сервера из README даёт только статические файлы, а не WS endpoint.

Путь сообщения:

```text
restartWsTimer() → makeWsMessage() → receiveWsMessage(JSON-строка)
  → проверка структуры и дублей
  → загрузка контекста через mockHttp.load(), если его нет в кэше
  → нормализация новой задачи со статусом open
  → очередь соответствующих даты и подразделения
  → сохранение демо и обновление UI
```

По умолчанию таймер работает каждые 10 секунд до 100 успешно принятых сгенерированных сообщений. Задачи адресуются дате и подразделению, выбранным в момент генерации. Предел и счётчик общие для всего демо. Длительности генератора чередуются: 30, 45, 60 минут; каждое пятое сообщение помечено эскалацией. Автоназначения специалисту нет.

Пауза, изменение интервала и предела описаны в [конфигурации](configuration.md). Пауза останавливает генератор, но не запрещает прямой приём через публичную функцию. Прямой приём не увеличивает счётчик генератора.

## Конверт сообщения

Обработчик `window.ReceiveWsMessage(serialized)` принимает **строку с JSON**:

```json
{
  "id": "message:example:1",
  "departmentId": "medical",
  "date": "2026-11-02",
  "event": {
    "id": "incoming:example:1",
    "work_type": "Диагностика",
    "model": { "id": "model:1", "name": "SV 300" },
    "client": { "id": "client:1", "name": "Демонстрационная клиника" },
    "duration": 45,
    "backups": null,
    "is_manual": false,
    "is_escalation": true,
    "priority": false,
    "description": "Проверить работу оборудования"
  }
}
```

- `id` — идентификатор доставки, `event.id` — идентификатор самой задачи. Это разные сущности; оба должны быть устойчивыми для повторной доставки.
- `departmentId` — известное приложению подразделение: из исходного `DEPARTMENTS` или списка подразделений текущих данных.
- `date` — строго `YYYY-MM-DD`, допустимая дата в диапазоне выбора 2000–2099.
- `event` — исходная модель одной задачи. Она поступает **в очередь**, даже если отправитель добавил поля назначения.
- `type` и версия протокола в текущем конверте не предусмотрены как обязательные поля. Изменение/удаление существующей задачи этим протоколом не реализовано.

Пример ручного события:

```json
{
  "id": "message:manual:1",
  "departmentId": "medical",
  "date": "2026-11-02",
  "event": {
    "id": "incoming:manual:1",
    "is_manual": true,
    "manual_type": "Обучение",
    "description": "Разбор новой сервисной инструкции",
    "duration": 60,
    "work_type": null,
    "model": null,
    "client": null,
    "backups": null,
    "is_escalation": false,
    "priority": false
  }
}
```

Допустимые ручные типы: «Событие», «Совещание», «Отгул», «Обучение». Для них нужны непустое описание и положительная целая длительность.

## Валидация и результат

| Проверка | Ограничение |
| --- | --- |
| Вход | Только строка; максимум 100 000 единиц длины JavaScript-строки, не байт сетевого пакета |
| ID сообщения и задачи | Непустая строка, максимум 200 единиц длины строки |
| Длительность | `Number.isSafeInteger(duration)` и `duration > 0` |
| Флаги | `is_manual`, `is_escalation`, `priority` при наличии строго boolean |
| Обычная задача | Непустой `work_type`, корректный объект `model` с `id` и `name` |
| Ручная задача | Разрешённый `manual_type`, непустая строка `description` |
| Необязательные поля | Тексты, модель, заказчик и компетенции проходят общую валидацию; объекты вместо текстовых полей отклоняются |
| Реестр доставок | До 2000 уникальных принятых ID сообщений; после этого новые отклоняются до сброса демо |

Функция возвращает Promise с одним из результатов:

```json
{ "accepted": true }
```

```json
{ "accepted": false, "duplicate": true }
```

```json
{ "accepted": false, "error": true }
```

```json
{ "accepted": false, "cancelled": true }
```

`error` означает отклонённые данные или ошибку получения контекста. Текст причины показывается в панели потока; поле с текстом ошибки в результате не возвращается. `cancelled` применяется, когда сброс демо сделал ожидающий приём неактуальным. Это результат локального вызова, **не ACK, отправленный серверу**.

Проверяется повторный ID сообщения либо ID задачи среди всех кэшированных контекстов, включая назначенные и завершённые задачи. Дубликат не меняет существующую задачу, её статус и историю. Новый ID доставки с прежним `event.id` также считается повтором, а не обновлением.

После асинхронной загрузки контекста проверка дублей повторяется. Принятые ID сохраняются вместе с демо; сброс очищает их. Это локальная защита от дублей, не гарантия exactly-once для распределённой системы.

## Как проверить приём вручную

1. Откройте [отдельное демо с фиксированными часами](http://127.0.0.1:8765/?mockStorage=memory&mockNow=2026-11-02T09:37).
2. Дождитесь загрузки и при желании поставьте автоматический поток на паузу.
3. Раскройте диагностическую форму WS, доступную при `mockStorage=memory`, вставьте один из JSON-примеров выше и отправьте его.
4. Выберите медицинское подразделение и 2 ноября 2026 года, если открыт другой контекст. Новая задача появится в очереди со статусом «Открыта».
5. Повторите тот же JSON: результат — повтор пропущен, второй карточки нет. Для другой новой задачи измените оба ID.

Альтернатива в консоли браузера на странице приложения:

```js
(async () => {
  const message = {
    id: `message:${crypto.randomUUID()}`,
    departmentId: 'medical',
    date: '2026-11-02',
    event: {
      id: `incoming:${crypto.randomUUID()}`,
      is_manual: true,
      manual_type: 'Совещание',
      description: 'Обсуждение плана работ',
      duration: 30,
      backups: null,
      is_escalation: false,
      priority: false
    }
  };
  const result = await window.ReceiveWsMessage(JSON.stringify(message));
  console.log(result);
})();
```

В обычном URL тот же вызов изменяет сохранённое демо; `mockStorage=memory` изолирует пример. Функция не требует, чтобы дата сообщения была открыта: задача сохраняется в целевой контекст, который затем можно выбрать.

## Почему карточка может появиться не сразу

Данные принимаются и сохраняются сразу после валидации. Перерисовка очереди откладывается во время открытого диалога, активного drag-and-drop или фокуса на карточке очереди, чтобы не прерывать действие. UI показывает уведомление о новых обращениях. После окончания действия список обновляется с сохранением прокрутки. Сообщение для другой даты/подразделения не добавляет карточку в текущую очередь.

## Подключение реального WS

Будущий адаптер транспорта должен передавать `MessageEvent.data` в `ReceiveWsMessage` как текстовую JSON-строку. Если сервер передаёт binary/Blob, сначала нужен согласованный декодер. Получение неизвестного контекста сейчас всё ещё вызывает `mockHttp.load()`: его тоже нужно заменить настоящей загрузкой, иначе реальные события смешаются с mock-расписанием.

Адрес сервера, подписки на подразделения/даты, права, восстановление после разрыва, повторная синхронизация и подтверждение доставки требуют отдельного серверного контракта. Сервер должен контролировать доступ и актуальность изменений. Клиентский флаг `permitted` управляет локальными действиями, а не авторизует доставку данных.
