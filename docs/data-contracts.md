# Модели данных и интерфейсы обновления

[← README](../README.md) · [Источники](architecture-and-mocks.md) · [WS](websocket.md)

Исходные модели основаны на пользовательской спецификации. Ниже описано поведение текущего [app.js](../app.js): `normalize()`, `validateTaskText()`, `updateData()` и `updateList()`. Это справочник реализованного адаптера; он не объявляет существующий удалённый API.

## Полный контекст расписания

Минимальный содержательный пример: один специалист, одно назначение и одно обращение в очереди.

```json
{
  "date_config": {
    "date": "2026-11-02T00:00:00",
    "time_begin": "0001-01-01T08:00:00",
    "time_end": "0001-01-01T17:00:00",
    "break_begin": "0001-01-01T12:00:00",
    "break_end": "0001-01-01T12:45:00"
  },
  "departments": [
    { "id": "medical", "name": "Медицинское оборудование", "is_current": true, "permitted": true }
  ],
  "engineers": [
    { "id": "medical-engineer-0", "name": "Алексей Смирнов" }
  ],
  "absences": [],
  "events": [
    {
      "id": "example:assigned:1",
      "work_type": "ТО",
      "model": { "id": "model:1", "name": "SLE 5000" },
      "client": { "id": "client:1", "name": "Демонстрационная клиника" },
      "duration": 60,
      "engineer": { "id": "medical-engineer-0", "name": "Алексей Смирнов" },
      "begin": "0001-01-01T08:00:00",
      "end": "0001-01-01T09:00:00",
      "backups": null,
      "is_manual": false,
      "is_escalation": false,
      "priority": false,
      "description": "Плановое обслуживание"
    }
  ],
  "new_events": [
    {
      "id": "example:queue:1",
      "work_type": "Диагностика",
      "model": { "id": "model:2", "name": "SV 300" },
      "client": null,
      "duration": 45,
      "backups": [
        { "id": "medical-engineer-0", "name": "Алексей Смирнов", "scoring_points": 0 }
      ],
      "is_manual": false,
      "is_escalation": true,
      "priority": true,
      "description": "Проверить работу оборудования"
    }
  ]
}
```

`events` — исходно назначенные задачи, `new_events` — очередь. ID задач должны быть уникальны между этими списками. ID и названия объектов справочников — непустые строки. Текущим считается первое подразделение с `is_current: true`, иначе первое в списке; для рабочего контекста передавайте одно текущее подразделение. Изменение разрешено только при `permitted === true`.

## Поля обращения

| Поле | Значение и смысл |
| --- | --- |
| `id` | Непустая строка; для WS дополнительно максимум 200 символов |
| `duration` | Положительное безопасное целое число минут, плановая длительность |
| `work_type` | Вид работ; строка или `null` в общем адаптере; для обычной WS-задачи обязательна непустая строка |
| `model` | `{ id, name }` или `null`; для обычной WS-задачи обязательна модель |
| `client` | Объект или `null`; поддерживаются строковые/null поля `id`, `name`, `client_id`, `client_name`, `client_address` |
| `description` | Строка или `null`; для ручного создания требуется непустое описание после trim |
| `last_period`, `client_date` | В fixtures имеют значение `null`; сохраняются в исходной модели, но текущая логика и UI их не используют |
| `backups` | Список компетентных специалистов, `null` или отсутствие поля; см. ниже |
| `is_manual` | Признак ручного события; для WS при наличии строго boolean |
| `manual_type` | Один из типов ручных событий, для обычной задачи может отсутствовать |
| `is_escalation` | Эскалация, независимая от статуса; `true` включает признак |
| `priority` | Признак приоритета; для WS при наличии строго boolean |
| `engineer` | `{ id, name }` специалиста из `engineers`, обязателен в `events` |
| `begin`, `end` | Начало и конец назначения, обязательны в `events` |

Общий нормализатор и WS-приёмник имеют разные уровни проверки: WS дополнительно требует вид работ/модель для обычной задачи и допустимый тип/описание для ручного события. Входящие тексты отображаются как текст, не как HTML.

### Компетенции

- `backups: null` или отсутствие обоих полей `backups`/`Backups` — ограничений по компетенциям нет.
- `backups: []` — нет подходящих специалистов; назначение запрещено.
- Непустой список — разрешены только перечисленные ID. Каждый элемент содержит `id`, `name`, необязательный `scoring_points`.
- Поддерживается историческое имя `Backups`, если поле `backups` не определено. Явное `backups: null` имеет приоритет над `Backups`.
- Скоринг `0` отображается как ноль. Если конечного числового скоринга нет, UI сообщает, что он не указан; членство в списке всё равно подтверждает компетенцию.

### Даты, время и отсутствия

Временные поля расписания принимают `0001-01-01THH:mm:00` либо дату контекста с тем же временем, например `2026-11-02T08:00:00`. Секунды должны быть `00`; суффикс `Z`, смещение и миллисекунды не поддерживаются. Время локальное, без преобразования из UTC. `end - begin` назначенной исходной задачи должно совпадать с `duration`, а интервал — помещаться в рабочий день.

Отсутствие содержит ссылку на известного специалиста:

```json
{
  "id": "absence:1",
  "type": "Отпуск",
  "id_engineer": { "id": "medical-engineer-0", "name": "Алексей Смирнов" },
  "begin": "2026-11-03T00:00:00",
  "end": "2026-11-04T00:00:00"
}
```

Проверка идёт по датам, **обе границы включены**: здесь недоступны 3 и 4 ноября целиком. Почасовые отсутствия эта модель не реализует. Ручной «Отгул» — обычное событие с длительностью и назначением, он не добавляет запись в `absences`.

Первичная нормализация проверяет форму данных и согласованность назначения, но не прогоняет каждую исходную задачу через полный `validateAssignment()`. Поэтому существующая задача на фоне отсутствия может отображаться как конфликт исходных данных. Новые назначения, переносы и изменения времени проходят полный валидатор.

## Отдельная модель задач и статусы

`normalize()` создаёт `tasks` поверх исходных `events`/`new_events`. Исходная модель доступна в `task.source`; прикладные поля отдельные:

| Поле | Назначение |
| --- | --- |
| `departmentId`, `date` | Контекст задачи |
| `assignment` | `{ engineerId, begin, end }`, где время — минуты от полуночи; `null` для очереди |
| `backups` | Нормализованные компетенции |
| `status` | Код статуса из таблицы ниже |
| `isEscalation` | Отдельный признак эскалации |
| `actualStartedAt`, `actualCompletedAt` | ISO-время факта или `null` |
| `plannedAssignment` | Исходный план завершённой задачи или `null` |
| `history` | Массив действий с временем и состоянием до/после |

| Код | Текст UI | Когда устанавливается |
| --- | --- | --- |
| `open` | Открыта | Новая задача без специалиста; возврат в очередь |
| `planned` | Запланирована | Назначение, перемещение или успешный перенос на завтра |
| `in_progress` | В работе | Явное начало работы; также задан в некоторых исходных mock-данных |
| `deferred` | Отложена | Откладывание назначенной задачи с освобождением места и возвратом в очередь |
| `completed` | Выполнена | Завершение; задача остаётся в календаре и доступна только для просмотра |

По умолчанию назначенная задача получает `planned`, неназначенная — `open`. Локальный `statusMapping` генератора задаёт некоторые другие начальные статусы. Поле `status` внутри исходной JSON-задачи само по себе этот mapping не заменяет.

Начать работу можно для сегодняшней запланированной задачи, когда наступило её назначенное время. Автоматического перехода по часам нет. Завершение допустимо из запланированного состояния и из работы: факт должен быть после начала назначенного интервала, не раньше фактического старта, если он есть, и не в будущем.

При досрочном завершении `assignment.end` сокращается до факта. `source.duration` остаётся плановой, а `plannedAssignment` хранит исходный интервал. Следующее назначение проверяет 30 минут от сокращённого конца. При позднем завершении факт и задержка фиксируются, но календарный интервал не растягивается на соседние задачи.

«Отложить» и «Вернуть в очередь» освобождают календарь, но дают разные статусы: `deferred` и `open`. Повторное назначение даёт `planned`. Перенос на завтра сохраняет ID, специалиста, время и длительность, сбрасывает текущие фактические поля и сохраняет прежние значения в истории. Выходной не пропускается автоматически; конфликт оставляет обе даты без переноса.

## Публичные функции обновления

Вызывайте после загрузки `app.js`; для обновления списков дождитесь успешной загрузки расписания. Функции доступны в консоли страницы или внешнему JavaScript на ней.

| Функция | Аргумент | Результат |
| --- | --- | --- |
| `UpdateData(value)` | Полный контекст из примера выше или его JSON-строка | Синхронный boolean |
| `UpdateEvents(value)` | Массив назначений, `null`, объект `{ events: [...] }` или их JSON-представление | Синхронный boolean |
| `UpdateNewEvents(value)` | Массив очереди, `null`, объект `{ new_events: [...] }` или их JSON-представление | Синхронный boolean |
| `ReceiveWsMessage(serialized)` | Только JSON-строка сообщения | Promise; см. [WS](websocket.md) |

`UpdateData` полностью заменяет выбранный ответом контекст, заново создаёт метаданные и статусы по умолчанию. История и фактические времена предыдущих задач автоматически не переносятся даже при тех же ID. Ошибка возвращает `false` и показывает экран ошибки загрузки.

`UpdateEvents` и `UpdateNewEvents` **заменяют весь соответствующий список**, а не добавляют элементы. `[]` или `null` очищает его. Второй список проектируется из актуальных задач. При том же ID, исходном плане и длительности сохраняются прикладные метаданные; для изменённых назначений не следует рассчитывать на сохранение прежнего факта. Некорректное обновление возвращает `false`, показывает сообщение и не меняет текущие данные.

Например, этот вызов очищает очередь в текущем контексте — выполняйте его только в изолированном демо:

```js
window.UpdateNewEvents({ new_events: [] });
```

Для добавления одной входящей задачи без удаления существующей очереди используйте `ReceiveWsMessage`. Вызов `UpdateNewEvents([однаНоваяЗадача])` заменит очередь этой задачей.
