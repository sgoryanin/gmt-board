# План реализации календаря обращений GMT Board

Дата подготовки: 2026-11-02, Europe/Samara.
Статус плана: **утверждён владельцем 2026-11-02**. Текущий объём сессии: GMT-08.
Основание: [спецификация](../specs/2026-11-02-dashboard-spec.md), утверждена владельцем в чате 2026-11-02.

## Результат и границы

Работающее статическое приложение из `index.html`, `styles.css`, `app.js`: русскоязычный светлый fluid-интерфейс, календарь специалистов, очередь обращений, drag-and-drop, ручные события, статусы, перенос на завтра, localStorage и WS-эмуляция. Основные сценарии проверяет исполнитель в живом браузере. Подробные продуктовые правила остаются в утверждённой спецификации; этот документ определяет порядок их реализации и проверки.

В качестве основы используются нативные HTML/CSS/JS, без прикладных фреймворков и без обязательных CDN-зависимостей. Сборщик, backend, настоящая интеграция с 1С/WS, авторизация, frontend unit-тесты и автоматические сканеры не добавляются. Git-записи остаются за владельцем. Публикация во внешнем сервисе в этот план не входит; результат запускается локально через HTTP.

Все восемь TODO выполняются последовательно: они меняют общие три файла приложения. Основной исполнитель владеет реализацией и проверками; независимый ревьюер проверяет законченный неизменяемый на время ревью блок. Обычно в одной рабочей сессии закрывается один согласованный TODO целиком. Переход к следующему пункту определяется назначенным владельцем объёмом сессии; дополнительных согласований обычных действий внутри утверждённого пункта нет.

## Структура и технические решения

| Файл | Ответственность |
| --- | --- |
| `index.html` | Семантическая структура страницы, панели, формы и модальные окна, подключение CSS/JS |
| `styles.css` | Цвета/типографика/отступы через CSS-переменные, Grid/Flex, шкала, карточки, адаптация и фокус |
| `app.js` | Конфигурация, mock-ответы, нормализация, состояние, правила планирования, операции, транспорт, отображение |
| `docs/development/plans/2026-11-02-dashboard-plan.md` | Единственный нумерованный checklist и фактические даты выполнения |
| `docs/MEMORY.md` | Согласования, текущий TODO, результаты, ограничения и следующая работа |
| `docs/verification/` | Краткие записи ревью/проверок и необходимые снимки интерфейса по TODO |

В `app.js` выделяются последовательные секции с ясными границами, без разнесения в дополнительные production JS-файлы:

1. Конфигурация и mock-наборы в исходном формате PDF.
2. Разбор календарных дат и минут, проверка входных данных, преобразование в `tasks`.
3. Состояние по подразделению/дате и чтение/запись одного версионированного снимка в localStorage.
4. Единая функция проверки назначения, возвращающая результат и русское объяснение отказа.
5. Операции назначения, снятия, статуса, завершения, междневного переноса.
6. Mock-HTTP, точки входа PDF, эмулятор сообщений и управление таймерами.
7. Отображение, формы, доступность, DnD и обработка пользовательских событий.

Изменения выполняются сначала в подготовленной копии состояния, проходят проверки и затем применяются одним действием. Отказ не оставляет промежуточных карточек. Исходный JSON не мутируется. `textContent`/DOM используются для пользовательских строк; произвольный HTML не исполняется. Видимые запреты дублируются в обработчиках действий.

Для воспроизводимых проверок времени используется единый внутренний источник текущего времени: в обычном демо — реальные часы, в ограниченной проверке — явно заданные mock-часы. Системное время не меняется; после проверки override убирается, в свидетельстве указывается применённый режим. Это позволяет проверять досрочное завершение и просрочку независимо от времени запуска проверки.

## Общий цикл каждого TODO

1. Записать фактическое начало с часовым поясом `+04:00`, реализовать только указанный объём.
2. Передать независимому ревьюеру точный набор изменений и критерии. Проверить корректность, авторизацию `permitted`, безопасность текстов/данных, сохранение состояния и относящиеся к пункту ограничения. Ревьюер не редактирует исходники.
3. Исправить замечания; повторить независимое ревью затронутых мест до разрешения замечаний. Самопроверка не называется независимым ревью.
4. Выполнить `node --check app.js` и применимые проверки проекта. Сборка статических файлов и backend units неприменимы; существующие применимые проверки не отключаются. Frontend unit-тесты не создаются.
5. Открыть работающее приложение в Google Chrome, выполнить перечисленные ниже сценарии через Playwright и/или Computer Use, осмотреть результат. Первичные пользовательские сценарии выполняются действиями в UI, а не прямыми вызовами функций изменения состояния. Узкие проверки обработки входных сообщений используют штатные адаптеры.
6. Исправить выявленные дефекты в текущем объёме, провести ревью исправлений и повторить затронутые проверки. Не перезапускать упавший сценарий без диагностики.
7. Записать фактические результаты, завершение и оставшиеся обязательства; обновить checklist и память. Неизменившиеся валидные результаты повторно не запускаются без причины.

Доступ к браузеру выбирается из действующих разрешённых возможностей. Отсутствие конкретного плагина не требует его установки. Не применяется headless/Mach-восстановление и обход запретов. Запуск приложения не зависит от доступности отдельного браузерного инструмента. Недоступная проверка отмечается `SKIPPED_ENVIRONMENT`, существенное непроверенное поведение оставляет TODO открытым.

## Риски и меры

| Риск | Мера в плане |
| --- | --- |
| Один большой JS-файл усложняет изменения | Секции с ясными контрактами, одна модель состояния и валидатор, последовательная работа и ревью каждого блока |
| Смещение времени и даты | Календарные даты и минуты без неявного UTC, отдельный разбор sentinel-даты, проверки границы дня/месяца/года |
| Ошибки DnD при скролле | Координаты относительно актуальной шкалы, единый preview/commit, живые действия после обеих прокруток |
| Потеря задачи между днями/очередью | Подготовка целого следующего состояния, проверка перед commit, единый снимок storage, проверки обеих дат после reload |
| WS сбрасывает действия пользователя | Контекст сообщения, дедупликация, сохранение локального workflow, точечные обновления и один таймер |
| Ложное выполнение по расписанию | Ручные подтверждения статусов, отдельные признаки наступившего срока/просрочки |
| Вёрстка слишком плотная | Минимальная ширина шкалы, отдельная очередь на узком экране, форма назначения, ранняя и итоговая визуальная проверка |
| Недоступен браузер/ревьюер | Продолжить независимую работу, точно записать недоступный этап; не объявлять его пройденным и не подменять независимое ревью самопроверкой |
