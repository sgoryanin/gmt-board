# Спецификация календаря обращений GMT Board

Дата: 2026-11-02, Europe/Samara. Статус: **утверждена владельцем 2026-11-02**.

Видимое название по уточнению владельца 2026-11-02: **ГМТ Доска**.

## Цель и границы

Разработать работающий демонстрационный дашборд распределения обращений по специалистам: дневной календарь, очередь обращений, переносы, ручные события, статусы и эскалация. Основой служат модели и эскиз из [Спецификации API](../../../Спецификация%20API.pdf), с уточнениями владельца от 2026-11-02.

Приложение состоит из одного HTML, одного CSS и одного JS файла. Используются HTML, CSS и JavaScript без React, Angular, Next.js и других прикладных фреймворков. CDN-зависимости допустимы, но не обязательны; базовый вариант использует браузерные возможности. Для зависимостей при необходимости фиксируется версия. Все пользовательские тексты русские, тема только светлая.

Данные синтетические. Настоящие HTTP API, WebSocket-сервер, 1С, серверная авторизация и многопользовательская синхронизация в эту версию не входят. Эмулятор воспроизводит получение и обработку сообщений; интерфейс явно обозначает режим демо. Модальное окно действий специалиста демонстрирует сценарий без имитации защищённой учётной записи.

## Согласованные решения

| Область | Решение владельца |
| --- | --- |
| Интервал | Между любыми событиями одного специалиста минимум 30 минут, включая ручные события |
| Обед | Настраиваемый запрещённый интервал; никакие задачи и события не могут его пересекать |
| Привязка при переносе | Начало привязывается к сетке 15 минут |
| Обратный перенос | Задачу можно снять с календаря и вернуть в очередь |
| Демо | Сохранение в localStorage, сброс демо, разделение состояния по датам и подразделениям |
| Статусы | Отдельная модель приложения поверх исходных JSON, значения по умолчанию, изменение через модальное окно |
| Эскалация | Отображается в первой версии отдельно от статуса |
| Перенести на завтра | Сохранить специалиста и время; проверить целевой день; при конфликте сохранить исходное состояние |
| Отложить | Освободить календарь, вернуть в очередь со статусом «Отложена» |
| Завершить досрочно | Сохранить карточку в календаре, сократить занятость до фактического завершения; следующий интервал отсчитывать от него |
| UI | Fluid-дизайн, читаемость и доступность, адаптация к доступному экрану |
| Проверка | Самостоятельно открыть приложение в браузере и проверить основные сценарии через Playwright в Google Chrome и/или Computer Use |

## Экран и поведение интерфейса

Верхняя панель содержит название, выбор подразделения, текущую дату, навигацию по дням, переход к сегодняшнему дню и индикатор демопотока. Недельная полоса служит быстрым переключателем выбранного дня, календарь отображает один день. Рабочие часы берутся из конфигурации выбранной даты, а не из подписей эскиза.

Под панелью располагается компактная сводка назначенных обращений по видам работ и общей загрузке. Ручные события учитываются в занятости, но не выдаются за ремонт или ТО. Загрузка специалиста — сумма занятого времени / длительность рабочего дня без обеда; 30-минутные промежутки не считаются выполненной работой.

Основная область — календарь: слева специалисты, горизонтально рабочее время, внутри строк карточки событий. Имена специалистов и заголовок шкалы закреплены при прокрутке. Обед видимо обозначен и подписан; отсутствие выделяет строку с причиной. Если у отсутствующего специалиста уже есть назначения из входных данных, они остаются видимыми с предупреждением и доступными для снятия или переноса.

Карточка календаря показывает вид работ или ручного события, модель оборудования при наличии, интервал, длительность, статус и эскалацию. Сокращённый текст раскрывается в карточке подробностей по нажатию; сведения доступны не только по наведению. Для необязательных данных не выводятся `null`, `undefined` или пустые подписи.

Правая панель содержит очередь, количество обращений, поиск по видимым данным, сортировку и кнопку «Создать событие». Обычные обращения идут раньше ручных; сортировка по срочности и длительности действует внутри этих групп. Эскалированные обращения выделены в отдельную группу этой же очереди, без дублирования карточек. Для ручных событий сохраняется размещение внизу. В полном списке доступны все обращения, в том числе при отсутствии результатов поиска показывается понятное пустое состояние.

Эскалация — независимый флаг `is_escalation`, а не этап выполнения. В этой версии она поступает из mock-данных и сообщений. Пользовательский процесс объявления/снятия эскалации не определён исходным контрактом и не включён в модальное окно статусов. Назначение эскалированного обращения выполняется по тем же ограничениям.

### Fluid-дизайн и доступность

- Контейнер занимает доступную ширину без фиксированного макета и искусственных широких полей; CSS Grid/Flex распределяют пространство.
- На широком экране очередь находится справа; ориентир ширины панели 300–380 CSS px. Календарь получает оставшееся пространство.
- При недостатке ширины очередь открывается отдельной панелью по кнопке с количеством задач. Назначение через форму доступно и без одновременного показа очереди и календаря.
- Временная шкала имеет минимальную читаемую ширину и собственную горизонтальную прокрутку. Страница и модальные окна не создают непредусмотренного горизонтального скролла. Карточки не сжимаются для искусственного размещения всего дня на телефоне.
- Проверяемые размеры: 1920×1080, 1440×900, 1280×800, 768×1024 и 390×844 CSS px. Проверяется также масштаб браузера 200%.
- Основной текст ориентировочно 14–16 px; вторичные подписи остаются читаемыми. Насыщенный синий и зелёный используются на светлых поверхностях, тёмный текст — на пастельных карточках.
- Контраст обычного текста не ниже 4.5:1, крупных надписей и важных границ элементов — не ниже 3:1. Цвет дополняется текстом/иконкой; статус не передаётся только цветом.
- Кнопки и поля имеют явные названия и состояния. Целевые области основных действий не меньше 44×44 CSS px. Видимый фокус, логичный Tab-порядок, доступные сообщения об ошибках и результаты действий.
- Модальные окна получают фокус, удерживают его до закрытия, закрываются Escape и возвращают фокус инициатору. Ошибки связаны с полями. На малой высоте прокручивается содержимое окна, действия остаются достижимыми.
- Анимации сдержанные, учитывается `prefers-reduced-motion`. Приход новых обращений не закрывает окно, не сбрасывает прокрутку и не отменяет ввод.

## Данные и совместимость с PDF

Сохраняются исходные структуры `id_department`, `id_engineer`, `id_model`, `id_client`, `date_config`, `id_absence`, `id_event`, `id_new_event`. Массивы и необязательные поля обрабатываются согласно примерам JSON.

| Поле или особенность | Правило обработки |
| --- | --- |
| `backups` | Массив допустимых специалистов. Отсутствующее поле или `null` означает отсутствие ограничения; пустой массив означает отсутствие подходящих специалистов |
| `Backups` в таблице PDF | На входе допускается как вариант написания; внутри приложения используется `backups` |
| `scoring_points` | Показывается для соответствующего специалиста во время назначения; `0` — действительный балл, `null` не заменяется нулём |
| `permitted` | Планирование и изменения разрешены только при `true`; отсутствующее/некорректное значение не предоставляет право редактирования |
| `is_current` | Выбирается первое подразделение с `true`; если такого нет — первое из массива |
| `0001-01-01T…` | Время суток, объединяемое с выбранной датой; не реальное событие первого года |
| Локальные даты без смещения | Обрабатываются как календарные дата и время без скрытого пересчёта в UTC |
| `absences.begin/end` | Включительные календарные даты отсутствия на весь день |
| `duration` | Положительное целое число минут; конечная граница должна согласовываться с длительностью |
| Необязательные свойства | Отсутствующие значения корректно допускаются; поля вида работ/модели/заказчика у ручных событий не требуются |

Исходные объекты не мутируются. После загрузки создаётся единый список `tasks`, объединяющий назначенные и неназначенные обращения, со служебными полями приложения. Один `id` не должен порождать карточки одновременно в очереди и календаре.

Пример структуры слоя приложения, не изменяющий контракт 1С:

```js
const task = {
  id: source.id,
  source: structuredClone(source),
  departmentId,
  date,
  assignment: null,
  status: 'open',
  isEscalation: source.is_escalation === true,
  actualStartedAt: null,
  actualCompletedAt: null,
  history: [],
};
```

Для назначенных задач `assignment` содержит идентификатор специалиста и начало/конец. Исходные плановые границы сохраняются отдельно от сокращённого интервала занятости при досрочном завершении. История содержит действие, время и предыдущие/новые значения; это локальная история демо, не серверный аудит.

Сохраняются точки входа `UpdateData`, `UpdateEvents`, `UpdateNewEvents`. `UpdateData` перестраивает выбранный контекст; `null` означает отсутствие соответствующего блока в новом контексте, а не сохранение данных другого дня. Частичные процедуры заменяют соответствующий список текущего контекста. Новое WS-сообщение добавляет/обновляет одну сущность через тот же слой нормализации. Повтор сообщения с тем же идентификатором не создаёт дубль и не сбрасывает локальный статус.

Имена действий PDF `ChangeDate`, `ChangeDept`, `MoveEvent`, `NewPlanning`, `NewUserEvent` сохраняются в mock-адаптере. Браузер не переходит по искусственным HTTP-ссылкам из примера 1С. Для возврата в очередь и изменения статусов применяются явно локальные действия; реальный контракт этих операций будет отдельной интеграционной задачей.

## Правила планирования

1. Задача целиком помещается в рабочий день и не пересекает обед. Окончание ровно в начале обеда или начало ровно после обеда допустимы.
2. Запрещены пересечения с другими событиями. Между окончанием предыдущего и началом следующего события одного специалиста должно быть не меньше 30 минут. Проверка выполняется с обеих сторон нового интервала.
3. Время обеда может входить в промежуток между задачами. Дополнительные 30 минут до и после самого обеда не требуются. Пример: событие до 12:00 и следующее с 12:45 допустимы при обеде 12:00–12:45.
4. Для ручных событий исключений по обеду и промежуткам нет. Длительное событие, которое не помещается в непрерывный разрешённый интервал, не назначается; автоматического разделения на части нет.
5. Отсутствие специалиста на выбранную дату запрещает новое назначение, а ограниченный `backups` требует совпадения идентификатора специалиста.
6. В режиме просмотра разрешены выбор подразделения/даты и чтение данных; создание, назначение, перенос и смена статуса запрещены и в интерфейсе, и в обработчиках.
7. Перенос привязывает новое начало к четверти часа и сохраняет длительность. Длительность не обязана быть кратна 15 минутам. Завершённые карточки не перетаскиваются; изменение длины карточки мышью не входит в эту версию.
8. Проверка повторяется непосредственно перед применением действия. Ошибка не изменяет ни очередь, ни календарь и объясняет конкретную причину. Автоматического поиска другого времени вместо выбранного нет.

Drag-and-drop поддерживает очередь → календарь, перенос по времени, перенос между специалистами и календарь → очередь. При наведении показываются предполагаемые границы, доступность строки, причина запрета и скоринг. При прокрутке расчёт позиции учитывает смещение шкалы; Escape отменяет перенос. Для клавиатуры и узких экранов предусмотрена форма назначения с выбором специалиста/времени и теми же проверками.

## Статусы и действия специалиста

| Код | Подпись | Правило |
| --- | --- | --- |
| `open` | Открыта | Начальное значение для неназначенного обращения или созданного ручного события |
| `planned` | Запланирована | Есть назначение; специалист ещё не подтвердил начало |
| `in_progress` | В работе | Специалист явно выбрал «Начать работу» |
| `deferred` | Отложена | Назначение снято действием «Отложить», задача находится в очереди |
| `completed` | Выполнена | Специалист подтвердил завершение; карточка сохраняется в календаре |

По умолчанию назначенные задачи получают `planned`, неназначенные — `open`. Для демонстрации остальных состояний используется отдельный mock-маппинг по `id`, применяемый после нормализации. Он не добавляет поля в исходные JSON-объекты. Сохранённые изменения пользователя имеют приоритет над демонстрационным маппингом.

Утверждённое правило: ход времени не запускает и не завершает работу автоматически. У задачи с наступившим началом, но без подтверждения начала, остаётся «Запланирована» с отметкой «Время начала наступило». При превышении планового окончания незавершённой задачи появляется отметка просрочки. Это вычисляемый признак, а не замена рабочего статуса.

Нажатие карточки открывает модальное окно с данными обращения, текущим назначением, статусом и доступными действиями. Переходы выполняются атомарно:

- **Назначить:** `open`/`deferred` → `planned`, удаление из очереди только после успешной проверки.
- **Вернуть в очередь:** снятие незавершённого назначения, статус `open`. **Отложить:** аналогичное снятие, но статус `deferred`. История предыдущего назначения сохраняется.
- **Начать работу:** `planned` → `in_progress`, фиксируется текущее время. Действие доступно для выбранного сегодняшнего дня при наступившем времени начала. Самовольное раннее расширение интервала занятости не производится.
- **Завершить:** `planned`/`in_progress` → `completed`, фиксируется фактическое время. Нельзя завершить задачу до начала её назначенного интервала или в будущем относительно часов демо.
- **Завершить досрочно:** фактическое завершение находится строго после начала и раньше планового конца. Конец занятого интервала сокращается до фактического времени с точностью до минуты, длительность пересчитывается; новая задача допустима не раньше чем через 30 минут. Привязка 15 минут применяется к новой задаче, а не округляет факт завершения. Исходный план остаётся в подробностях.
- **Позднее завершение:** в подробностях фиксируется фактическое время и задержка. Плановый слот автоматически не расширяется поверх соседних задач; время сверх плана явно обозначено как факт, а не свободно перепланированное назначение.
- **Перенести на завтра:** незавершённая задача переносится на следующий календарный день относительно её текущего назначения с теми же специалистом, временем и длительностью; статус становится `planned`. Проверяются график и назначения целевого дня, обед, отсутствие, компетенция и право изменения. Если день нерабочий или слот занят, операция отклоняется целиком. Автоматического перехода к следующему рабочему дню нет.

Для переноса используются исходное подразделение и его календарь. После успешного действия текущий день остаётся открыт, сообщение предлагает перейти к целевой дате. Завершённые события доступны для чтения; повторное открытие и редактирование истории выполнения не входят в эту версию.

## Создание ручного события

Модальное окно содержит тип из четырёх значений PDF, обязательное описание и длительность в минутах. Длительность — положительное целое число; пустое описание и некорректная длительность блокируют сохранение с сообщениями у полей. HTML из описания не исполняется.

После успешного mock-вызова создаётся уникальный `id`, устанавливаются `is_manual: true`, `manual_type`, `description`, `duration`, статус `open`; событие появляется внизу очереди текущего контекста. До подтверждения успешного создания повторная отправка заблокирована. Закрытие окна без сохранения не создаёт событие.

## Конфигурация и mock-транспорт

Конфигурация приложения включает `slotStepMinutes: 15`, `minGapMinutes: 30`, `mockWsIntervalMs: 10000`, режим демопотока и параметры генерации mock-данных. Рабочее время и обед задаются через `date_config.time_begin/time_end/break_begin/break_end`. Некорректный график не допускается молча: показывается ошибка конфигурации, назначения блокируются.

Базовый mock-график: 08:00–17:00, обед 12:00–12:45; несколько подразделений, одно из них только для просмотра. Даты образцов PDF переносятся на текущую дату демо. Начальное расписание содержит специалистов разной загрузки, ограниченные компетенции, отсутствие с конфликтующим старым назначением, обычные/срочные/эскалированные/ручные события. Для завтрашнего дня есть как свободные, так и занятые слоты для проверки переноса.

Mock-HTTP возвращает Promise с задержкой и исходными моделями; файлы JSON допустимы, но для компактной поставки набор может находиться в `app.js`. В интерфейсе предусмотрены состояния загрузки, ошибки и повторной попытки. Изменение подразделения/даты не позволяет запоздавшему ответу перезаписать уже выбранный контекст.

Mock-WebSocket воспроизводит сообщения с сериализованным JSON, идентификатором, подразделением и датой. Интервал по умолчанию 10 секунд, меняется через настройки демо; доступны пауза/возобновление. Обработчик проверяет форму данных и принимает только корректные обращения. Новые карточки приходят в очередь, не назначаются автоматически и не получают фактический статус работы.

Повторная инициализация, смена даты, настройка интервала и сброс не создают дополнительные таймеры. Сообщение обрабатывается в указанном в нём контексте и не переносится в другое подразделение из-за переключения интерфейса. Для длительно открытой демонстрации действует конфигурируемый предел генерации; при достижении показана пауза, существующие задачи не удаляются.

## Сохранение состояния

localStorage содержит версию схемы, состояния по подразделению/дате, статусы, назначения, историю и настройки демопотока. Перенос между днями сохраняет обе стороны одной операцией состояния, не создавая дубль. Обновление страницы восстанавливает изменения без повторного наполнения начальными данными.

Кнопка «Сбросить демо» с подтверждением очищает только ключи GMT Board, восстанавливает mock-данные и единственный таймер. Ошибка доступа к хранилищу не обрушает интерфейс: работа продолжается в памяти с явным предупреждением, что изменения не сохранятся после перезагрузки. Повреждённые/несовместимые данные не исполняются и не выдаются за успешно восстановленные.

## Организация и стиль реализации

```text
index.html                         Структура интерфейса и модальные окна
styles.css                         Все собственные стили и адаптация
app.js                             Конфигурация, mock-данные, адаптеры, состояние, UI
docs/development/specs/             Спецификация и принятые решения
docs/development/plans/             План и датированные TODO после утверждения спеки
docs/verification/                 Краткие результаты и материалы проверок
docs/MEMORY.md                      Контекст, согласования, оставшаяся работа
```

Внутри одного JS файла разделяются нормализация данных, единая проверка назначения, операции состояния, транспорт и отображение. Нет нескольких несовместимых валидаторов для DnD, форм и переноса на завтра. Идентификаторы/комментарии английские, UI русский; пользовательский текст вставляется безопасно как текст. Комментарии описывают действующее поведение, без ссылок на рабочие планы и отчёты.

Предполагаемые команды из корня проекта:

```bash
python3 -m http.server 8080 --bind 127.0.0.1
node --check app.js
```

Сборка не нужна для статических файлов. Frontend unit-тесты не создаются. При занятом порте используется свободный порт, чужой процесс не останавливается. Запуск/остановка только проверенного процесса текущей задачи.

## Проверка и критерии приёмки

После утверждения спецификации и затем подробного плана выполняются реализация, независимое ревью с проверкой безопасности, исправления и повторное ревью. Далее — синтаксические и применимые проектные проверки, затем запуск приложения и живые сценарии в Google Chrome через Playwright и/или Computer Use. Наличие дополнительных линтеров не предполагается без проверки проекта. Backend unit-тесты и backend build неприменимы, поскольку backend отсутствует.

Результат проверяется самим исполнителем в браузере. Проверяются внешний вид, читаемость, расположение карточек и модальных окон, прокрутка, ошибки консоли, запросы и реальные изменения состояния. Автоматическая проверка DOM не заменяет визуальный осмотр.

| Сценарий | Ожидаемый результат |
| --- | --- |
| Начальная загрузка | Русский светлый UI, заполненный календарь и очередь, корректные статусы и сводка |
| Fluid и масштаб | На всех контрольных размерах доступны действия; имена/шкала закреплены, нет наложений и нечитаемого сжатия |
| Корректное назначение | Задача переходит из очереди в выбранный слот, получает «Запланирована», сохранение переживает перезагрузку |
| Граница промежутка | 15 минут между событиями запрещены, ровно 30 разрешены; проверка с обеих сторон |
| Обед и рабочий день | Пересечение обеда и выход за рабочие часы запрещены, граничные допустимые интервалы принимаются |
| Компетенции и отсутствие | Недопустимый специалист отклонён с причиной; доступный показывает скоринг, включая 0 |
| Перепланирование и возврат | DnD между специалистами/временем и обратно работает без дублей, ошибок смещения и потери карточек |
| Назначение через форму | Клавиатура/узкий экран дают тот же результат и ограничения, что DnD |
| Ручное событие | Валидация формы, создание в очереди, последующее назначение; текст с HTML отображается как текст |
| Отложить | Слот освобождён, очередь содержит одну задачу «Отложена» |
| Перенести на завтра | Успех сохраняет специалиста/время; конфликт не меняет исходные данные; после перезагрузки обе даты согласованы |
| Статусы и досрочное завершение | Модальное окно меняет статус; занятость сокращается до факта, 30 минут считаются от нового конца |
| Эскалация | Отдельный признак и группа видимы, назначение проходит общую валидацию |
| WS-эмуляция | Новая задача приходит после интервала, смена интервала/пауза работают, дубли и неверный контекст не портят состояние |
| Асинхронность | Новое сообщение не прерывает DnD/ввод; запоздавший ответ не возвращает старый день |
| Только просмотр | Чтение доступно, все пользовательские изменения заблокированы |
| Доступность | Tab, фокус, Escape, возврат фокуса и сообщения ошибок работают; статус различим без цвета |
| Сброс и хранение | Сброс подтверждается, затрагивает только GMT Board; восстановление или ошибка хранения отражают реальное состояние |

Результаты отмечаются PASS/FAIL/SKIPPED_ENVIRONMENT с кратким фактическим свидетельством. Недоступный браузерный сценарий не объявляется пройденным; существенное непроверенное поведение остаётся открытым. Глобальные регрессии, автоматические сканеры и дополнительные обязательные runtime-гейты не добавляются.
