# Архитектура, mock-источники и получение данных

[← README](../README.md) · [Конфигурация](configuration.md) · [Контракты](data-contracts.md) · [WS](websocket.md)

## Какие классы замоканы

В текущей реализации **нет классов сервисов** и отдельного mock-сервера. Весь JavaScript находится в [app.js](../app.js), внутри функции-замыкания. Источники представлены обычными объектами и функциями:

| Компонент | Что имитирует или делает | Где вызывается |
| --- | --- | --- |
| `mockResponse(departmentId, date)` | Генератор ответа расписания, справочников, отсутствий и очереди | `mockHttp.load()` |
| `mockHttp.load(departmentId, date)` | Асинхронное получение расписания с задержкой/ошибкой | `loadContext()`, `loadTomorrow()`, `receiveWsMessage()` для неизвестного контекста |
| `mockHttp.loadTomorrow(departmentId, date, signal)` | Получение целевого расписания перед переносом | `moveToTomorrow()` |
| `mockHttp.NewUserEvent(context, input, signal)` | Создание ручного события и выдача UUID | `submitCreation()` |
| `makeWsMessage()` и `restartWsTimer()` | Генератор входящих WS-подобных сообщений по таймеру | При старте, настройке, возобновлении и сбросе потока |
| `receiveWsMessage(serialized)` | Приём и проверка входящего сообщения, добавление в очередь | Эмулятор, диагностическая форма, публичный `ReceiveWsMessage` |
| `storage` | В обычном режиме обёртка над настоящим `localStorage`; в тестовых режимах — память и ошибки | `restoreDemo()`, `saveDemo()`, `resetDemo()` |

`DEPARTMENTS`, `NAMES`, `MODELS`, `WORK_TYPES`, `MANUAL_TYPES`, `CLIENTS` — локальные справочники и исходные данные. Имена, адреса, модели и обращения используются как демонстрационные примеры. В `medical` генерируются 12 специалистов, в остальных подразделениях — 7. Будние дни предзаполняются назначениями; очередь формируется отдельно. Некоторые исходные сценарии специально показывают отсутствие, отсутствие компетенций, эскалацию и различные статусы.

Ни `mockHttp`, ни его метод `NewUserEvent` не доступны как `window.mockHttp`/`window.NewUserEvent`. Их имена обозначают внутренние методы, а не существующие HTTP endpoints.

## Путь от запуска до экрана

```text
index.html → styles.css + app.js
  → restoreDemo(): восстановление localStorage или тестовой памяти
  → loadContext(): выбор даты и подразделения
      → contexts.get("departmentId:date"), если контекст уже есть
      → иначе mockHttp.load() → mockResponse() → normalize()
  → applyData(): актуальное состояние, кэш, сохранение, отрисовка
  → restartWsTimer(): дальнейшие входящие обращения
```

`contexts` — `Map` контекстов по паре «подразделение + дата». `state` хранит текущий контекст, поиск, сортировку, состояние загрузки и номер запроса. Смена даты или подразделения вызывает `loadContext()`. Устаревшие ответы после переключения не должны перезаписывать текущий экран: используется `requestId`.

`mockResponse()` возвращает `{ raw, statusMapping }`. `raw` соответствует исходным JSON-моделям, а `statusMapping` — локальный JavaScript `Map` для начальных демонстрационных статусов, не поле JSON API. `normalize()` строит из них отдельный список `tasks` с назначением, статусом и историей. Детали полей — в [контрактах](data-contracts.md).

## Где происходят запросы

Статический HTTP-сервер обслуживает HTML, CSS, JS и другие запрошенные файлы. В прикладной части **нет `fetch`, `XMLHttpRequest` и `new WebSocket`**. Задержки `mockHttp` реализованы через таймеры и Promise; JSON-файлы с данными с диска не загружаются.

Поэтому в Network браузера не будет REST-вызовов создания, назначения или смены статуса, а в разделе WS не будет соединения. Для изменения fixtures редактируйте `mockResponse()` и справочники, затем учитывайте [восстановление кэша](configuration.md).

## Как изменяются задачи

| Действие | Точка входа в коде | Что меняется |
| --- | --- | --- |
| Назначить / переместить / вернуть в очередь | `planningActions.NewPlanning`, `MoveEvent`, `ReturnToQueue` → `commitPlanning()` | Назначение, статус, фактические поля и история |
| Проверить доступность назначения | `validateAssignment()` | Только результат проверки; общий для формы, DnD и переноса на завтра |
| Создать ручное событие | `submitCreation()` → `mockHttp.NewUserEvent()` | После ответа событие добавляется в очередь текущего при старте запроса контекста |
| Начать / отложить / завершить | `commitStatus()` → `validateStatus()` | Статус, фактическое время, занятый интервал и история |
| Перенести на завтра | `moveToTomorrow()` → `mockHttp.loadTomorrow()` | Проверяются обе стороны; затем задача удаляется из исходного и добавляется в целевой контекст |
| Получить входящее обращение | `receiveWsMessage()` | Добавляется задача в очередь указанного контекста, сохраняется ID сообщения |

Перечисленные действия меняют локальное состояние. Настоящего серверного сохранения нет. Создание и перенос отменяются при закрытии диалога/смене контекста; используются `AbortController` и проверки актуальности операции. Перенос на завтра публикует обе стороны без промежуточного `await`, чтобы снимок не содержал только половину переноса. Это атомарность локального изменения, не транзакция удалённой базы.

`raw` сохраняет исходный формат ответа; `tasks` содержит текущую модель интерфейса. Назначения и статусы нельзя надёжно читать только из старого `raw`: локальные изменения хранятся в метаданных задач. `saveDemo()` записывает обе части, `restoreContext()` восстанавливает и валидирует их.

## Интерфейсы для внешнего источника

Публичны только четыре функции:

- `window.UpdateData(value)` — полная замена текущего контекста исходным ответом.
- `window.UpdateEvents(value)` — замена списка назначенных событий.
- `window.UpdateNewEvents(value)` — замена очереди.
- `window.ReceiveWsMessage(serialized)` — асинхронное добавление одного входящего обращения.

Это вызовы JavaScript на странице, не HTTP-маршруты. Форматы и правила замены описаны в [контрактах](data-contracts.md) и [WS](websocket.md).

## Подключение настоящего сервера: точки изменения

Этот раздел описывает будущую интеграцию; сейчас она не реализована.

1. Замените внутренние методы `mockHttp` адаптером к согласованному API. `load()` должен дать данные для `normalize()`, создание — исходную модель нового события. Сохраните отмену и защиту от устаревших ответов.
2. Добавьте серверные операции назначения, перемещения, возврата, статусов и атомарного переноса между датами. Сегодня эти операции выполняются только локально; одной замены `mockHttp.load()` недостаточно.
3. Для WS передавайте текст сообщения в `ReceiveWsMessage`. Отключите демо-генератор, чтобы он не смешивал mock и реальные обращения. Согласуйте адрес, авторизацию, reconnect, повторную синхронизацию и подтверждения доставки — текущего сетевого контракта для них нет.
4. Определите серверное представление статусов, истории и фактического времени. Полная `UpdateData()` по исходному контракту не переносит локальную историю автоматически.
5. Повторяйте на сервере проверку прав, интервалов, компетенций и конкурентных изменений. `permitted` в браузерных данных — демонстрационный режим UI, а не граница авторизации.
6. Решите, должен ли `localStorage` оставаться кэшем после подключения сервера. Текущее сохранение не реализует синхронизацию, разрешение конфликтов или совместную работу нескольких пользователей.

Конкретные URL, HTTP-методы и схема аутентификации намеренно не заданы: существующего backend-контракта для этих операций в приложении нет.
